# استودیو — Eventها

Event نقطه شروع، انتظار، واکنش به یک رخداد یا پایان مسیر فرآیند است. با انتخاب نوع مناسب، می‌توانید فرآیند را با اقدام کاربر، موعد زمانی، ارسال داده موبایل یا فراخوانی بیرونی آغاز کنید؛ برای انجام یک کار مهلت بگذارید؛ اجرای مسیر را تا زمان مشخصی نگه دارید؛ یا خطای یک فعالیت را به مسیر رسیدگی بفرستید.

## انتخاب رویداد مناسب

| نیاز | رویداد | محل قرارگیری و نتیجه |
| --- | --- | --- |
| آغاز فرآیند توسط کاربر مجاز | Start Event | ابتدای مسیر؛ با شروع کاربر، نمونه جدید ایجاد می‌شود |
| خاتمه مسیر و تعریف خروجی نهایی | End Event | انتهای مسیر؛ خروجی‌های تعریف‌شده در پایان قابل استفاده‌اند |
| ایجاد نمونه جدید طبق برنامه زمانی | Timer Start Event | ابتدای مسیر؛ هر نوبت زمان‌بندی، اجرای جدیدی آغاز می‌کند |
| محدودکردن مهلت انجام UserTask | Timer Boundary Event | روی مرز کار؛ با تمام‌شدن مهلت، کار جاری خاتمه می‌یابد و مسیر مرزی ادامه پیدا می‌کند |
| توقف مسیر تا موعد یا مدت معین | Timer Intermediate Catch Event | میان دو گام؛ کار بعدی پس از پایان انتظار ایجاد می‌شود |
| رسیدگی به خطای اجرای یک فعالیت | Error Boundary Event | روی مرز فعالیت؛ خطا ثبت می‌شود و مسیر رسیدگی ادامه می‌یابد |
| آغاز فرآیند از داده ارسالی یک کار همراه نامحدود | Graph Mobile Start Event | ابتدای مسیر؛ ارسال رکورد به سرور محرک شروع است |
| امکان تکمیل کار از کارتابل یا از فراخوانی بیرونی | Message Boundary Event | روی مرز UserTask؛ یکی از دو راه تکمیل می‌تواند مسیر را جلو ببرد |
| شروع فرآیند از دکمه فرم یا درخواست سرویس | Message Start Event | ابتدای مسیر مقصد؛ فراخوانی مجاز، نمونه جدید را شروع می‌کند |

رویداد میانی مستقل را روی خط اصلی مسیر قرار دهید. رویداد مرزی باید به بدنه فعالیت میزبان متصل باشد؛ نزدیک‌بودن ظاهری آن به فعالیت کافی نیست. برای رویداد مرزی، مسیر خروجی مستقلی رسم کنید تا مقصد واکنش مشخص باشد.

برای افزودن رویداد، در استودیوی فرآیند شکل مناسب را روی بوم قرار دهید، منوی تغییر نوع آن را باز کنید و نوع موردنظر را برگزینید. سپس عنوان، اتصال‌ها و تنظیمات اختصاصی را تکمیل کنید. دایره شروع، رویداد میانی و رویداد پایان محل یکسانی در مدل ندارند؛ پیش از انتخاب علامت داخلی، محل استفاده را مشخص کنید.

**تنظیمات مشترک:** **عنوان** و **توضیحات** رویداد و ذخیره تغییرات از پنل استودیو در دسترس‌اند. برای کار با پنل و بوم به استودیوی فرآیند مراجعه کنید؛ زمان، خروجی، داده آغاز یا رفتار مرزی را در بخش اختصاصی همان رویداد تنظیم کنید.

## Start Event؛ شروع توسط کاربر

![نماد Start Event](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=3C08B844-5113-41C9-ABE0-E767DC8B047F)

Start Event

برای فرآیندی که کاربر باید آن را از فهرست فرآیندهای قابل اجرا آغاز کند، Start عادی را در ابتدای مسیر قرار دهید. آن را به نخستین Task وصل کنید و مسیر را تا پایان ادامه دهید.

1.  Start را داخل Lane شروع‌کننده قرار دهید.
2.  دسترسی شروع را در همان Lane تنظیم کنید؛ برای نمونه، یک نقش یا کاربر مشخص.
3.  خروجی Start را به نخستین گام متصل کنید.
4.  فرم، داده و دریافت‌کنندگان گام‌های بعدی را تکمیل کنید.
5.  فرآیند را ذخیره و نسخه موردنظر را برای اجرا فعال کنید.
6.  با کاربر و نقش مجاز، فرآیندهای قابل شروع را باز و اجرای آن را بررسی کنید.

دسترسی Start به آغاز نمونه مربوط است. اینکه پس از آغاز، کار به چه کسی ارجاع شود، به Lane و تنظیمات Task مقصد بستگی دارد. جابه‌جایی Start به Lane دیگر می‌تواند دسترسی آغاز را تغییر دهد؛ جابه‌جایی کار بعدی نیز می‌تواند گیرنده آن کار را عوض کند. تنظیم کامل نقش، کاربر و دسترسی متغیری در Pool و Lane آمده است.

### تنظیمات عمومی Event و شروع عادی

پنل تنظیمات هر Event، نوع نماد و شناسه آن را در بالای صفحه نمایش می‌دهد. عنوان برای نام‌گذاری خوانای گام روی بوم به‌کار می‌رود؛ توضیحات، شرح تکمیلی همان گام است. دکمه «تنظیمات رفتارها و عملکردها» و آیکون راهنمای بخش‌های اختصاصی را با تنظیمات ویژه نوع Event اشتباه نگیرید.

ویرایشگر توضیحات ابزارهای اندازه و خانواده قلم، قالب متن، ضخیم، مورب، زیرخط، تراز، فهرست و درج محتوا دارد. در فیلد عنوان، علامت × برای پاک‌کردن مقدار در دسترس است.

[![پنل Start Event برای تعیین عنوان و توضیحات آغاز عادی](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=C115C20C-6615-43E8-BAA9-2C417A29A21A)](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=C115C20C-6615-43E8-BAA9-2C417A29A21A "بازکردن تصویر در اندازه اصلی")

پنل Start Event برای تعیین عنوان و توضیحات آغاز عادی

Start Event عادی ورودی شروع دستی Process از مسیر «کارتابل فرآیند ← فرآیندهای قابل شروع» است. دسترسی آغاز از Lane حاوی آن تعیین می‌شود؛ بنابراین نخست Lane شروع را تنظیم کنید و سپس مسیر خروجی Start را به گام بعد وصل کنید. عنوانی مانند «شروع درخواست» به کاربر کمک می‌کند ورودی درست مدل را تشخیص دهد.

## پیش‌نیاز اجرای زمان‌بندی

Timer Start، Timer Boundary و Timer میانی به اجرای فعال زمان‌بند وابسته‌اند. ذخیره یک علامت ساعت روی مدل، زمان‌بند را فعال نمی‌کند. پیش از طراحی و بررسی سناریوی زمانی، تنظیمات وب‌سایت، حساب اجرای تایمر و موتور زمان‌بندی را آماده کنید.

### تنظیم وب‌سایت و Application Pool

در IIS، وب‌سایت میزبان GraphBPMS و Application Pool مربوط به همان وب‌سایت را مشخص کنید. تنظیمات را روی همان استقرار انجام دهید تا تایمر به برنامه و پایگاه داده موردنظر متصل باشد.

1.  در **Advanced Settings** وب‌سایت، **Preload Enabled** را روی **True** قرار دهید.
2.  در **Advanced Settings** مربوط به Application Pool، **Start Mode** را روی **AlwaysRunning** قرار دهید.
3.  آدرس پایه برنامه را با آدرس قابل دسترسی از خود سرور تطبیق دهید؛ پورت و مسیر برنامه نیز باید درست باشند.
4.  پیکربندی حساب اجرای تایمر و فعال‌سازی موتور را تکمیل کنید.
5.  پس از تغییر تنظیمات، Application Pool را Recycle و وب‌سایت را Restart کنید تا تنظیمات جدید در برنامه بارگذاری شوند.

[![تنظیم Start Mode در Advanced Settings مربوط به Application Pool](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=85D009A1-2A42-4E25-9B8A-12F9D150B29B)](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=85D009A1-2A42-4E25-9B8A-12F9D150B29B "بازکردن تصویر در اندازه اصلی")

تنظیم Start Mode در Advanced Settings مربوط به Application Pool

_مقدار_ _AlwaysRunning_ _را برای Application Pool وب‌سایت GraphBPMS انتخاب کنید._

### پیکربندی موتور و حساب اجرا

پارامترهای زمان‌بند در تنظیم سیستمی `DynamicTimerConfigs` نگهداری می‌شوند. آدرس پایه، نام کاربری و رمز حساب تایمر باید با همان محیط هماهنگ باشند. حساب سیستمی اجرای فرآیند، مانند حساب اختصاصی `BpmsTimer`، باید فعال و قابل احراز هویت باشد؛ قفل‌شدن حساب یا نامعتبر بودن رمز، اجرای داخلی تایمر را مختل می‌کند.

| تنظیم | مقدار موردنیاز |
| --- | --- |
| `DynamicTimerConfigs` | پیکربندی زمان‌بند همان استقرار |
| `custom.appUrl.baseUrl` | آدرس پایه برنامه که سرور به آن دسترسی دارد |
| `custom.appUser.userName` | نام حساب اختصاصی اجرای تایمر |
| `custom.appUser.password` | رمز معتبر همان حساب |
| `EnableTimer` | مقدار `true` در تنظیمات برنامه برای فعال‌شدن موتور |

برای رفع خطای احراز هویت، وضعیت حساب، تلاش‌های ناموفق و تطابق رمز را بررسی کنید. پس از تغییر نام یا رمز حساب اجرای تایمر، مقدار متناظر را در پیکربندی زمان‌بند نیز اصلاح کنید.

پس از هر تغییر مؤثر در آدرس پایه، حساب یا فعال‌سازی تایمر، برنامه را دوباره راه‌اندازی کنید. سپس صفحه مدیریت تایمر را باز کنید و فعال‌بودن زمان‌بند را بررسی کنید. برنامه زمانی یک فرآیند باید با شناسه همان نسخه در فهرست کارهای زمان‌بندی‌شده قابل شناسایی باشد.

> **نکته — آدرس بیرون از محیط محلی:** استفاده از `HTTP` برای آدرس غیرمحلی به تنظیمات ارتباطی زیرساخت برنامه وابسته است. آدرس و پروتکل را با پیکربندی همان محیط هماهنگ کنید؛ صرف تغییر آدرس پایه، این پیش‌نیاز را برطرف نمی‌کند.

### جزئیات عمومی Timer

در برنامه Timer Start بخش‌های دقیقه و ساعت باید فعال و کامل باشند. روز، ماه یا سال غیرفعال به حالت همه تبدیل می‌شود. در تعیین بازه سال، ابتدای بازه نباید بزرگ‌تر از انتها باشد. گزینه‌های روز شامل روزهای هفته یا ماه، الگوی افزایشی، روزهای مشخص، آخر ماه یا هفته، آخرین روز انتخابی هفته در ماه، فاصله تا انتهای ماه و بازه روز هفته یا ماه است. زمان‌بندی با ساعت و منطقه زمانی سرور انجام می‌شود.

در Timer Boundary، انتخاب روش زمان ضروری است؛ مدت دستی کاملاً صفر یا متغیر موعد خالی پذیرفته نمی‌شود. فیلد تعداد تکرار در نسخه مستندشده غیرفعال است و نباید به‌عنوان قابلیت تکرار تایمر مرزی آموزش داده شود. کلید `custom.error.retryInterval` در پیکربندی عمومی زمان‌بند، فاصله تلاش دوباره پس از خطای زمان‌بند را برحسب دقیقه تعیین می‌کند؛ این مفهوم با تکرار کسب‌وکاری Timer Boundary متفاوت است.

## Timer Start؛ آغاز طبق برنامه زمانی

![نماد Timer Start Event](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=1B7BE9CD-DD74-4D54-852E-01DAA12A1D7F)

Timer Start Event

Timer Start برای کاری مناسب است که باید بدون شروع دستی کاربر و در زمان‌های مشخص اجرا شود؛ برای نمونه بررسی دوره‌ای درخواست‌های منقضی‌شده یا اجرای یک سرویس نگهداری داده. هر نوبت شروع زمان‌بندی‌شده، نمونه جدیدی ایجاد می‌کند. این رفتار را با نگه‌داشتن یک نمونه موجود در Timer میانی اشتباه نگیرید.

### ساخت مسیر زمان‌بندی‌شده

1.  Start را روی بوم قرار دهید و نوع آن را به Timer Start تغییر دهید.
2.  عنوان روشنی برای شروع زمانی بنویسید.
3.  آن را به کار بعدی وصل کنید؛ برای مسیر کاملاً خودکار می‌تواند ServiceTask باشد.
4.  ادامه کار و End را متصل کنید.
5.  Timer Start را انتخاب و **تنظیمات زمان اجرای فرآیند** را باز کنید.
6.  نوع تقویم و برنامه زمانی را ��نظیم و تأیید کنید.
7.  فرآیند را ذخیره کنید و اجرای تایمر این نسخه را از عملیات مدیریتی آغاز کنید.

در یک فرآیند یک Timer Start تعریف کنید. همین فرآیند می‌تواند علاوه بر مسیر زمانی، Start عادی و مسیر شروع دستی نیز داشته باشد. برای نمونه، در یک Lane مسیر دستی ثبت درخواست قرار می‌گیرد و در Lane دیگر مسیر زمانی بررسی دوره‌ای درخواست‌ها اجرا می‌شود.

[![مسیر مستقل Timer Start به سرویس و پایان در همان فرآیند](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=50696667-F113-4AD8-9E6A-54048230CBB3)](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=50696667-F113-4AD8-9E6A-54048230CBB3 "بازکردن تصویر در اندازه اصلی")

شروع زمانی، سرویس دوره‌ای و پایان، یک مسیر مستقل از مسیر ثبت دستی تشکیل می‌دهند.

> **مثال — پاک‌سازی درخواست‌های بی‌نتیجه:** یک سرویس دوره‌ای می‌تواند درخواست‌هایی را پاک کند که هم نتیجه بررسی آن‌ها خالی مانده و هم تاریخ پایانشان گذشته است. هر دو شرط را با هم در عملیات سرویس لحاظ کنید تا درخواست‌های تأییدشده یا درخواست‌های دارای زمان معتبر وارد این پاک‌سازی نشوند. مسیر این کار از Timer Start به ServiceTask و سپس End می‌رود؛ تنظیم خود سرویس در مقاله Taskها و Activityها توضیح داده شده است.

### انتخاب تقویم و زمان اجرا

در پنجره زمان‌بندی، تقویم میلادی یا شمسی را متناسب با تقویم کاری انتخاب کنید. سپس بخش‌های دقیقه، ساعت، روز، ماه و سال را تنظیم کنید. انتخاب تقویم باید پیش از نهایی‌کردن مقادیر روز و ماه روشن باشد.

[![تنظیم زمان اجرای فرآیند با تقویم و بخش‌های برنامه زمانی](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=CBB17435-5DA2-469E-B681-543CBB096624)](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=CBB17435-5DA2-469E-B681-543CBB096624 "بازکردن تصویر در اندازه اصلی")

برنامه زمانی را از بخش‌های پنجره بسازید و نتیجه را همراه نوع تقویم بررسی کنید.

| بخش | انتخاب‌های کاربردی |
| --- | --- |
| دقیقه و ساعت | هر مقدار، شروع از مقدار معین با گام مشخص، مقادیر منتخب یا بازه |
| روز | روزهای هفته یا ماه، روزهای مشخص و الگوهای انتهای ماه یا هفته |
| ماه | همه ماه‌ها، ماه‌های منتخب، افزایش با گام یا بازه |
| سال | همه سال‌ها، سال‌های منتخب، افزایش با گام یا بازه |

برای اجرای آزمایشی هر دقیقه، برنامه را طوری بسازید که همه دقیقه‌ها و ساعت‌ها و روزهای موردنظر را پوشش دهد. این فاصله فقط انتخاب سناریو است؛ برای کار دوره‌ای واقعی، تناوب را براساس حجم کار و نیاز کسب‌وکار تعیین کنید.

برای محدودکردن اجرا به سال‌های مشخص، بازه سال را همراه ماه‌ها، روزها و ساعت‌های موردنظر تعیین کنید. انتخاب آخرین روز ماه نیز برای کارهایی مانند آماده‌سازی صورتحساب پایان ماه کاربرد دارد. نتیجه برنامه را در مدیریت تایمر با موعد اجرای موردنظر تطبیق دهید.

در تنظیمات نهایی، دقیقه و ساعت را فعال و کامل کنید. اگر روز، ماه یا سال را محدود می‌کنید، محدوده‌ها را با تقویم انتخاب‌شده تطبیق دهید. برای بازه سال، ابتدای بازه نباید از انتهای آن بزرگ‌تر باشد. رشته زمان‌بندی تولیدشده را صرفاً با یک عبارت Cron پنج‌بخشی سیستم‌عامل جایگزین نکنید؛ برنامه زمانی را با همین پنجره بسازید.

زمان اجرای کار به ساعت و منطقه زمانی سرور وابسته است. اگر موعدی که در مدیریت تایمر دیده می‌شود با انتظار شما فاصله دارد، علاوه بر شرط‌های تقویم، ساعت و منطقه زمانی سرور را بررسی کنید.

پیش‌نمایش نمونه زمان‌بندی محدود به یک سال مشخص

در نمونهٔ جدول برنامه، دقیقه‌ها `1-5` و ساعت `0` انتخاب شده‌اند؛ یعنی محدودیت دقیقه و ساعت جداگانه تنظیم می‌شود. مقدار روز ماه در تصویر `L-30`، ماه `*`، روز هفته `?` و سال `2026` است. تعبیر دقیق `L-30` در تقویم و موتور همین سامانه نیازمند تأیید فنی است؛ آن را بدون بررسی به «روز سی‌ام» یا «روز سی‌ویکم» تبدیل نکنید.

با محدودکردن سال به یک سال یا بازه مشخص، پس از پایان همان محدوده نوبت زمان‌بندی بعدی ایجاد نمی‌شود. این محدودیت، تکرار داخل محدوده را از بین نمی‌برد: مثلاً برنامه می‌تواند در ساعت‌های انتخاب‌شده هر ۱۰ دقیقه اجرا شود، اما فقط در سال ۲۰۲۶. محدودبودن دوره و تکرارشونده‌بودن درون دوره دو تنظیم مستقل‌اند؛ این توضیح رفتار Timer Start را با انتظار Timer میانی یا مهلت Timer مرزی یکسان نمی‌کند.

برای نمونهٔ پرداخت دوره‌ای حقوق، Timer Start می‌تواند در روز انتخابی ماه فرآیندی را آغاز کند که فهرست کارکنان و اطلاعات حقوق را می‌خواند و به مراحل بعدی می‌رود. معتبر بودن روز منتخب را در ماه‌ها و تقویم برنامه بررسی کنید؛ وجود روز سی‌ویکم را برای همه ماه‌ها فرض نکنید. آغاز فرآیند اعلان دوره‌ای نیز کاربرد دیگری از همین زمان‌بندی است.

### Lane شروع تایمری و هویت اجرای زمان‌بندی

با قرارگرفتن Timer Start در Lane، سامانه دسترسی آن Lane را به «کاربر مجری فرآیند» اختصاص می‌دهد و پیام مربوط به ا��ن تغییر را نمایش می‌دهد. تنظیم دسترسی مبتنی بر کاربر و انتخاب حساب مجری در پنجره سطح دسترسی قابل مشاهده است. تنظیمات دسترسی این Lane به حالت Read-only درمی‌آید و امکان جایگزین‌کردن آن با کاربران دیگر وجود ندارد.

اگر علاوه بر شروع تایمری به شروع دستی نیاز دارید، Start عادی را در Lane جداگانه با دسترسی کاربران یا نقش‌های کاری قرار دهید. وجود هر دو Start در یک Lane باعث می‌شود دسترسی کل Lane از Timer Start تأثیر بگیرد. سپس Sequence Flow هر ورودی را به گام مقصد متصل کنید. ورود با حساب مجری فرآیند برای دورزدن این تفکیک، الگوی شروع دستی کاربران نیست.

انتساب خودکار Lane شروع تایمری به کاربر مجری فرآیند

اگر بعد از اجرای خودکار به اقدام یک کاربر کاری نیاز است، User Task مقصد باید در Lane با دسترسی مناسب همان کاربر یا نقش قرار گیرد. هویت اجرای زمان‌بند الزاماً هویت درخواست‌کننده نیست؛ در قواعدی که به کاربر جاری، نقش جاری یا مافوق آن‌ها وابسته‌اند، گیرنده بعد از تایمر را با هویت کسب‌وکار محاسبه کنید.

فعال‌کردن Timer Start، تنظیمات عمومی موتور زمان‌بندی را جایگزین نمی‌کند. آماده‌سازی IIS، حساب اجرای تایمر، آدرس برنامه، DynamicTimerConfigs و EnableTimer باید مطابق بخش «آماده‌سازی اجرای تایمر» همین مقاله انجام شود.

خود ورودی Timer Start فقط با محرک زمان‌بندی آغاز می‌شود؛ آن را از «فرآیندهای قابل شروع» مانند Start عادی، با فراخوانی بیرونی مانند Message Start، یا با Broadcast مانند Signal Start آغاز نمی‌کنید. اگر مدل به این محرک‌ها هم نیاز دارد، ورودی مناسب هر محرک را جداگانه طراحی کنید.

### تعیین دریافت‌کننده کار انسانی بعد از تایمر

تایمر فرآیند را با حساب اجرای سیستمی شروع می‌کند. اگر UserTask بعد از آن باید به یک کاربر کاری برسد، آن را در Lane با دریافت‌کننده صریح قرار دهید. نگه‌داشتن کار انسانی در زمینه اجرای تایمر می‌تواند باعث شود کار به حساب سیستمی برسد و در کارتابل کاربر موردنظر دیده نشود.

برای نمونه، مسیر `Timer Start → ServiceTask → End` می‌تواند کاملاً خودکار باشد. اگر بعد از شروع زمانی نیاز به تأیید انسان دارید، UserTask تأیید را در Lane با کاربر یا نقش مناسب قرار دهید و وصول واقعی آن را در کارتابل همان گیرنده بررسی کنید.

### شروع، توقف و شناسایی تایمر نسخه

پس از ذخیره مدل، در لیست و مدیریت فرآیندها عملیات **شروع تایمر** همان نسخه را اجرا کنید. سپس در مدیریت تایمر، کار ثبت‌شده را با شناسه فرآیند و موعد اجرای آن تطبیق دهید. برای متوقف‌کردن شروع‌های بعدی، از **توقف تایمر** استفاده کنید.

فعال‌بودن نسخه و شروع تایمر دو تنظیم جدا هستند. برای بررسی اجرا، هم نسخه هدف و هم وضعیت برنامه زمانی آن را کنترل کنید. متوقف‌کردن Timer Start، شروع دستی از Start عادی همان مدل را به خودی خود حذف نمی‌کند.

### کنترل نتیجهٔ عملیات زمان‌بندی‌شده

زمان «اجرای قبلی» در مدیریت تایمر، به‌تنهایی اثر کسب‌وکاری سرویس را ثابت نمی‌کند. پس از یک نوبت اجرا، نمونهٔ ایجادشده، وضعیت گام سرویس و دادهٔ هدف را نیز کنترل کنید. در مثال پاک‌سازی درخواست‌های منقضی و بی‌نتیجه، تعداد رکوردهای مشمول دو شرط را پیش و پس از اجرا مقایسه کنید؛ صرف جابه‌جایی زمان اجرای بعدی کافی نیست. این بررسی را روی دادهٔ آزمون انجام دهید و فقط نتیجهٔ همان دامنه را به موفقیت عملیات نسبت دهید.

## قرارداد مقدار Timer میانی و مرزی

Timer میانی مسیر را پیش از ایجاد گام بعد نگه می‌دارد. Timer مرزی به فعالیت میزبان متصل است و برای آن مهلت تعیین می‌کند. قرار دادن شکل ساعت نزدیک User Task کافی نیست؛ نماد مرزی باید به بدنه همان Task متصل باشد و Sequence Flow خروجی مستقل داشته باشد.

| تنظیم | رفتار |
| --- | --- |
| انتخاب نوع مقدار: مقدار دستی | میزان توقف با اجزای ماه، روز، ساعت و دقیقه تعیین می‌شود. نمونه یک‌دقیقه‌ای: صفر ماه، صفر روز، صفر ساعت و یک دقیقه. |
| انتخاب نوع مقدار: انتخاب از متغیر | متغیر موعد را انتخاب کنید؛ حالت ساده مقدار ابتدایی را مصرف می‌کند و حالت پیشرفته برای تعیین مسیر داده به‌کار می‌رود. |
| استفاده از شرح ارجاع سفارشی | فعال‌سازی تنظیم شرح ارجاع برای ادامه ناشی از تایمر. |
| ذخیره تنظیمات | ثبت تنظیمات اختصاصی Timer پس از تکمیل مقادیر. |

در روش دستی، مقدار یک فاصله زمانی است؛ در روش متغیر، موعد تاریخ و ساعت مورد انتظار است. عدد 1 در Variable را خودبه‌خود معادل یک دقیقه فرض نکنید. داده موعد باید به تاریخ و ساعت قابل تفسیر تبدیل شده باشد؛ برای داده ساختاریافته، مسیر عضو مناسب را تعیین کنید.

## Intermediate Timer Catch؛ انتظار میان گام‌ها

![نماد Intermediate Timer Catch Event](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=A0D054FF-A33D-41D6-BE7C-7B62CE66E9CB)

Intermediate Timer Catch Event

Timer Intermediate Catch Event مسیر جاری را تا زمان تعیین‌شده نگه می‌دارد. کار بعدی هنوز ایجاد نشده است؛ پس از پایان انتظار، مسیر ادامه می‌یابد و اگر مقصد UserTask باشد، آن زمان به گیرنده ارجاع می‌شود.

برای نمونه، پس از تأیید درخواست یک دقیقه فاصله قرار دهید و سپس کار بررسی مدیر را ایجاد کنید. اگر روی کار مدیر نیز Timer Boundary قرار داده باشید، مهلت مدیر بعد از ایجاد همان کار آغاز می‌شود. فاصله قبل از ارجاع و مهلت پاسخ بعد از ارجاع دو انتظار جدا هستند.

### افزودن انتظار به مسیر

1.  در محل فاصله موردنظر، رویداد میانی اضافه کنید و نوع Timer Catch را انتخاب کنید.
2.  خروجی گام قبلی را به آن وصل کنید.
3.  خروجی تایمر را به گامی که باید پس از انتظار انجام شود متصل کنید.
4.  روش مدت دستی یا موعد متغیری را با همان معنای شرح‌داده‌شده برای تایمر تنظیم کنید.
5.  فرآیند را ذخیره کنید و اجرا را تا رسیدن به تایمر ادامه دهید.
6.  پیش از موعد، نبودن کار بعدی در کارتابل را بررسی کنید؛ پس از موعد، ایجاد همان کار را ببینید.

ساعت در مسیر اصلی قرار دارد؛ شروع کار بعدی به پایان این انتظار وابسته است.

### انتظار میانی با مقدار دستی یا Variable

Intermediate Timer با رسیدن جریان به آن، زمان تعیین‌شده منتظر می‌ماند و سپس مسیر عادی را ادامه می‌دهد. زمان می‌تواند مقدار دستی یا دادهٔ Variable باشد؛ برای Variable، روش ساده یا پیشرفته و مسیر عضو مناسب را انتخاب کنید.

### حفظ هویت کاری هنگام ادامه از تایمر

ادامه خودکار از تایمر با حساب و نقش سیستمی اجرای تایمر انجام می‌شود. بنابراین **کاربر جاری** و **نقش جاری** در آن نقطه الزاماً همان درخواست‌کننده یا آخرین بررسی‌کننده نیستند. این تفاوت روی قواعد ارجاعی مانند انتخاب بالادست نقش جاری اثر دارد.

> **نکته — گیرنده بعد از انتظار:** اگر بعد از تایمر باید کار به مدیر درخواست‌کننده برسد، مقصد را از هویت درخواست‌کننده محاسبه کنید. انتخاب بالادست حساب تایمر ممکن است کار را به مدیر حساب سیستمی بفرستد. صرف جابه‌جایی شکل تایمر به Lane درخواست‌کننده، هویت اجرای خودکار را به او تبدیل نمی‌کند.

دو الگوی کاربردی برای تعیین گیرنده عبارت‌اند از:

-   هویت یا نقش لازم را پیش از انتظار در متغیر نگه دارید؛ گیرنده کسب‌وکار را براساس همان داده محاسبه و در دسترسی متغیری Lane مقصد استفاده کنید.
-   وقتی فرآیند برای یک بخش مشخص طراحی شده است، شروع را به نقش همان بخش محدود و Lane بررسی بعد از تایمر را به نقش مدیر همان بخش نسبت دهید.

برای بازگشت کار به شخصی که واقعاً قبلاً اقدام کرده است، تنظیم نمایش کارتابل براساس کاربر جاری و قواعد دریافت‌کننده را متناسب با مسیر در Pool و Lane بررسی کنید. گیرنده را با اجرای نمونه و کارتابل واقعی کنترل کنید؛ درست‌بودن نام Lane به‌تنهایی اثبات‌کننده درست‌بودن ارجاع نیست.

## قواعد مشترک رویدادهای مرزی

در GraphBPMS، **Timer Boundary** و **Message Boundary** برای **User Task** به کار می‌روند. Timer Boundary مهلت یک کار انسانی را کنترل می‌کند؛ آن را جای Timeout داخلی Script Task یا محدودیت اجرای Provider در Service Task قرار ندهید.

هر سه نوع Boundary موجود، Timer، Message و Error، **Interrupting** هستند: با وقوع رویداد، منطق جاری میزبان قطع می‌شود و مسیر مرزی ادامه می‌یابد. برای هر Boundary مسیر خروجی خودش را رسم کنید. نزدیک‌بودن Event به Task یا داشتن خروجی معمولی برای Task، جای اتصال مرزی و خروجی آن را نمی‌گیرد.

Timer Boundary Event

### اتصال رویداد به کار و طراحی مسیر مهلت

1.  رویداد مرزی را روی لبه UserTask قرار دهید و نوع Timer را انتخاب کنید.
2.  اتصال آن به بدنه همان کار را بررسی کنید.
3.  از خود رویداد مرزی یک Sequence Flow به مقصد پس از مهلت رسم کنید؛ برای مثال UserTask جانشین.
4.  مسیر عادی UserTask را نیز به مقصد اقدام کاربر متصل نگه دارید.
5.  Timer Boundary را انتخاب و روش تعیین زمان را تنظیم کنید.
6.  فرم و گیرنده کار مقصد مسیر مرزی را تکمیل و فرآیند را ذخیره کنید.

مدت را در قالب ماه، روز، ساعت و دقیقه وارد کنید؛ در این نمونه، فقط دقیقه برابر یک است. مدت را در قالب خود کنترل وارد کنید؛ مقدار کاملاً صفر برای تعیین مهلت معتبر نیست.

> **نکته — مدت نسبی و موعد مشخص:** این مقدار یک فاصله زمانی است. برای نمونه یک دقیقه از زمان ورود به کار محاسبه می‌شود؛ نوشتن ساعت روز در جای مدت، معنای تنظیم را تغییر می‌دهد. اگر نیاز به یک موعد تقویمی مشخص دارید، روش متغیر را انتخاب کنید.

### تعیین موعد از متغیر

در روش متغیر، مقدار ورودی تاریخ و ساعت موعد است. متغیر را در گامی پیش از انتظار آماده کنید؛ برای نمونه سرویس مقدار تاریخ و ساعت را برگرداند و خروجی آن در متغیر فرآیند قرار گیرد.

1.  روش متغیر را در تنظیم تایمر انتخاب کنید.
2.  متغیر حاوی موعد را مشخص کنید.
3.  اگر موعد عضو یک خروجی ساختاریافته است، حالت پیشرفته و مسیر عضو مناسب را تنظیم کنید.
4.  بررسی کنید مقدار نهایی یک تاریخ و ساعت میلادی قابل تفسیر باشد؛ مقدار `DateTime` یا `DateTime2` خروجی سرویس نمونه مناسبی است. می‌توانید موعد را پیش از رسیدن به تایمر با ScriptTask محاسبه و در متغیر ذخیره کنید؛ روش ساخت این خروجی در Taskها و Activityها آمده است.
5.  موعد را با ساعت مورد انتظار روی سرور تطبیق دهید.

> **نکته — نوع مقدار موعد:** متغیر حاوی عدد `1` به معنای «یک دقیقه بعد» نیست. همچنین نمایش شمسی یک تاریخ در فرم را بدون تبدیل مناسب به‌عنوان مقدار موعد ندهید. روش دستی، مدت نسبی می‌گیرد؛ روش متغیر، زمان وقوع را مشخص می‌کند.

### نتیجه اقدام کاربر و پایان مهلت

اگر کاربر پیش از موعد کار را ثبت کند، مسیر عادی UserTask ادامه می‌یابد و تایمر متعلق به آن انتظار لغو می‌شود. اگر مهلت تمام شود و کار هنوز منتظر باشد، کار از کارتابل دریافت‌کنندگان آن خارج و مسیر خروجی Timer Boundary اجرا می‌شود.

این انتقال، یک رونوشت اضافی برای جانشین نیست. کار قبلی دیگر برای ادامه عادی در اختیار دریافت‌کنندگان باقی نمی‌ماند. برای بررسی درست، هم کارتابل گیرنده قبلی و هم کارتابل مقصد مسیر مرزی را مشاهده کنید.

تایمرهای مرزی تک‌موعد پس از اجرای انتظار از فهرست انتظار زمان‌بند حذف می‌شوند. آن‌ها را با کار تکرارشونده Timer Start که همچنان برای نوبت‌های بعد وجود دارد مقایسه نکنید؛ شناسه فرآیند و نوع کار زمان‌بندی‌شده را هنگام بررسی تطبیق دهید.

اگر کاربر پیش از پایان مهلت User Task را ثبت کند، مسیر عادی ادامه می‌یابد و انتظار تایمر همان کار خاتمه پیدا می‌کند. اگر مهلت در زمان انتظار کار تمام شود، کار قبلی از دسترس اقدام خارج می‌شود و مسیر مرزی ادامه پیدا می‌کند. این انتقال به معنی ایجاد رونوشت اضافی از همان کار نیست.

### پایان مهلت و لغو انتظارهای همان کار

Timer Boundary روی User Task برای مهلت همان انتظار است. اگر زمان بگذرد و کاربر هنوز گام را ثبت نکرده باشد، User Task از کارتابل خارج می‌شود و جریان از خروجی Timer Boundary ادامه می‌یابد. Boundaryهای دیگر همان گام، مانند Message Boundary منتظر، نیز از مدار خارج می‌شوند؛ مسیرهای معلق آن گام پس از عبور Timer مستقل ادامه پیدا نمی‌کنند.

## Message Start؛ آغاز با فراخوانی بیرونی

![نماد Message Start Event](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=08E79FD4-85BB-413E-B9A9-C89C5C82B418)

Message Start Event

Message Start نقطه ورودی فرآیندی است که باید با فراخوانی یک فرم یا سرویس آغاز شود. برای نمونه، کاربر در یک فرم مستقل متن درخواست را می‌نویسد و با دکمه شروع فرآیند، آن متن را به متغیر ورودی فرآیند مقصد می‌فرستد.

### آماده‌سازی فرآیند مقصد

1.  Start را به نوع Message Start تغییر دهید.
2.  Lane شروع را برای کاربر یا نقش مجاز تنظیم کنید.
3.  متغیرهای ورودی موردنیاز مقصد را بسازید.
4.  مسیر بعد از Start را تکمیل کنید؛ مانند ServiceTask پردازش ورودی و UserTask نمایش نتیجه.
5.  End را به انتهای مسیر وصل و خروجی‌های لازم را در آن تعریف کنید.
6.  فرآیند را ذخیره و نسخه قابل اجرا را فعال کنید.

خود Message Start برای انتخاب سرویس فراهم‌کننده، پنل تنظیمات Message Boundary را ندارد. داده شروع از فراخواننده به متغیرهای فرآیند می‌رسد. مجازبودن شروع نیز باید با دسترسی Lane و هویت فراخوانی هماهنگ باشد.

### Message Start به‌عنوان ورودی فراخوانی بیرونی

برای شروع Process با سرویس عمومی GraphBPMS، REST API، ESB، دکمه Form یا Custom.js و RunProcess، ورودی Message Start را در مدل قرار دهید. این انتخاب فقط نحوه آغاز را تعیین می‌کند: Process می‌تواند پس از شروع بیرونی به User Task برسد و منتظر اقدام کاربر بماند.

فراخواننده باید دسترسی Lane حاوی Message Start را داشته باشد و فراخوانی را با ورودی‌ها و هویت معتبر انجام دهد. این مسیر آغاز با منوی فرآیندهای قابل شروع، زمان‌بندی Timer Start و دریافت Broadcast در Signal Start متفاوت است.

### Message Start و Message Boundary در رابط تنظیمات

Message Start نقطه آغاز یک نمونه جدید با فراخوانی بیرونی است؛ Message Boundary به User Task موجود متصل می‌شود و راه دیگری برای تکمیل انتظار جاری فراهم می‌کند. در تنظیم Message Start، پنل عمومی شناسه، عنوان، توضیحات و رفتارها نمایش داده می‌شود؛ داده آغاز از فراخواننده و Variableهای ورودی تأمین می‌شود.

### شروع از دکمه فرم

در فرم مبدأ، دکمه‌ای با عملکرد **شروع فرآیند** تنظیم کنید. فرآیند مقصد را انتخاب و عنوان نمونه و ورودی‌های آن را تعریف کنید.

1.  در تنظیمات دکمه، نوع عملکرد شروع فرآیند را انتخاب کنید.
2.  در **فرآیند مورد نظر**، مقصد دارای Message Start را برگزینید.
3.  **عنوان فرآیند** را تنظیم کنید. می‌توانید عنوان را از قطعات ثابت و مقادیر کنترلی یا سیستمی بسازید.
4.  برای افزودن هر قطعه عنوان، نوع و مقدار را تعیین و دکمه افزودن را بزنید؛ نتیجه نهایی را بررسی کنید.
5.  پارامترهای ورودی را تنظیم کنید؛ برای مثال متغیر مقصد `@@Var1` از مقدار یک کنترل متنی فرم مبدأ تغذیه شود.
6.  نحوه شروع، **به صورت سرویس** یا **به صورت معمولی**، را انتخاب کنید.
7.  فرم را ذخیره و با کاربر مجاز اجرا کنید.

برای عنوان ترکیبی، ترتیب قطعات را بررسی کنید تا جمله نهایی خوانا باشد. متن عنوان برای شناسایی نمونه است؛ مقدارهای موردنیاز منطق فرآیند را در پارامترهای ورودی جداگانه بفرستید.

در «نحوه شروع فرآیند»، حالت «به صورت سرویس» برای اجرای فراخوانی بدون بازشدن خودکار Form کار بعدی در همان محل و حالت «به صورت معمولی» برای نمایش ادامه Process است. در حالت معمولی، Target محل بازشدن را تعیین می‌کند؛ نمونه «بازکردن روی صفحه فعلی» است. «افزودن پارامتر» برای مقداردهی ورودی‌های Process مقصد به‌کار می‌رود. عنوان نمونه، ورودی منطق Process را جایگزین نمی‌کند.

### تفاوت شروع به صورت سرویس و معمولی

| نحوه شروع | رفتار قابل انتظار |
| --- | --- |
| **به صورت سرویس** | فرآیند اجرا می‌شود و نتیجه فراخوانی به فرم برمی‌گردد؛ UserTask ایجادشده می‌تواند در کارتابل قرار گیرد، اما فرم آن در همان محل به‌طور خودکار باز نمی‌شود |
| **به صورت معمولی** | شروع همراه با نمایش ادامه فرآیند است؛ می‌توانید بازشدن در صفحه فعلی یا تب جدید را تنظیم کنید |

در حالت سرویس، می‌توانید پس از موفقیت فراخوانی، پیام مناسب در فرم مبدأ نمایش دهید. این پیام نشان‌دهنده موفقیت شروع در همان مرحله است؛ به معنی پایان تمام کارهای انسانی فرآیند نیست. اگر مسیر به UserTask رسیده باشد، نمونه منتظر اقدام بعدی باقی می‌ماند.

در حالت معمولی، انتخاب صفحه فعلی یا تب جدید را متناسب با تجربه کاربر تعیین کنید. سپس هم نمایش فرم بعدی و هم وصول کار به گیرنده درست را بررسی کنید. تنظیم ظاهر شروع، دسترسی Lane مقصد را تغییر نمی‌دهد.

### شرط نمایش Form بعد از شروع معمولی

دکمه Form در حالت «به صورت سرویس»، Process را آغاز می‌کند و لازم نیست Form مقصد را در همان محل باز کند. در حالت «به صورت معمولی»، انتظار این است که Form User Task مقصد در صفحه فعلی یا صفحه جدید نمایش داده شود.

برای استفاده از این قابلیت، از Message Start تا User Task موردنظر نباید Node انتظارپذیر دیگری قرار داشته باشد. Nodeهای انتظارپذیر مطرح‌شده در موتور عبارت‌اند از User Task، Graph Mobile Task، Receive Task، Timer Intermediate Catch Event، Signal Intermediate Catch Event و Call Activity Task. User Task مقصد، پایان این مسیر قابل نمایش است؛ محدودیت مربوط به انتظارهای واسط پیش از رسیدن به آن است.

برای مثال، اگر مسیر ابتدا به Receive Task برسد، آن گام منتظر فراخوانی ادامه می‌ماند و هنوز Form User Task بعدی برای نمایش آماده نیست. در این مدل، تنظیم دکمه برای نمایش فوری Form با مسیر واقعی Process سازگار نیست.

### شروع با درخواست سرویس

برای فراخوانی از یک سرویس، درخواست `POST` به مسیر `/Process/RunProcess` در آدرس پایه برنامه بفرستید. درخواست باید با هویت معتبر انجام شود. اگر از توکن خصوصی استفاده می‌کنید، مقدار توکن حاصل از احراز هویت را در سرآیند `PrivateToken` قرار دهید.

در نگاشت خروجی احراز هویت، نام عضو داده را دقیق انتخاب کنید. برای خروجی دارای عضو `PrivateToken`، مسیر عضو همان `PrivateToken` است؛ حروف نام عضو JSON را با یک نام متفاوت جایگزین نکنید. مقدار واقعی توکن باید از خروجی احراز هویت همان اجرا گرفته شود.

| فیلد بدنه | کاربرد و نحوه تنظیم |
| --- | --- |
| `ProcessGroup` | شناسه گروه فرآیند؛ با تعیین آن، نسخه فعال گروه برای شروع انتخاب می‌شود |
| `Process` | شناسه یک نسخه مشخص؛ برای انتخاب از گروه، این فیلد را خالی بگذارید |
| `RunType` | برای Message Start مقدار `500002` |
| `Variables` | متغیرهای ورودی مقصد |
| `ProcessTitle` | عنوان نمونه جدید |
| `UserID` و `RoleID` | برای الگوی شروع با کاربر جاری، به‌ترتیب از متغیر **کاربر جاری** و **نقش جاری** مقداردهی کنید |
| `VerboseLevel` | مقدار اختیاری برای تعیین جزئیات پاسخ |

برای استفاده از نسخه فعال گروه، `ProcessGroup` را با شناسه واقعی گروه مقصد تنظیم و `Process` را خالی بگذارید. شناسه گروه و شناسه نسخه دو مقدار متفاوت‌اند؛ مقدار نمایش‌داده‌شده برای یک فرآیند را به فرآیند دیگر تعمیم ندهید.

> **نکته — انتقال ورودی:** پارامتر `Variables` را متناسب با ورودی‌های مقصد مقداردهی کنید. خالی‌گذاشتن آن، مقدارهای فرآیند فراخواننده را خودکار به مقصد نمی‌فرستد؛ اگر مقدار لازم را ارسال نکنید، کنترل نمایش‌دهنده آن در مقصد می‌تواند خالی باشد.

حداقل یکی از شناسه‌های گروه یا نسخه لازم است. برای استفاده از نسخه فعال گروه، فقط `ProcessGroup` را مبنای انتخاب قرار دهید؛ وقتی هر دو مقدار داده شوند، انتخاب گروه بر شناسه نسخه تقدم دارد. هیچ‌یک از شناسه‌های یک محیط را بدون جایگزینی با شناسه واقعی مقصد در محیط دیگر استفاده نکنید.

ارسال UserID یا RoleID در بدنه به‌تنهایی مجوز اجرای فرآیند یا جانشینی کاربر ایجاد نمی‌کند. رابطهٔ این فیلدها با هویت توکن و هویت مؤثر اجرا باید طبق قرارداد همان endpoint و استقرار کنترل شود. برای جزئیات نام ورودی، پوستهٔ پاسخ و احراز هویت، [مرجع فنی API و Custom JS](PROCESS-10-API-CUSTOMJS.html) را ببینید.

ساختار هر ردیف متغیر ورودی، نام و مقدار است. برای نمونه، اگر مقصد متغیری به نام `@@Var1` دارد، بخش `Variables` می‌تواند چنین باشد:

این قطعه فقط محتوای فیلد `Variables` است. نام متغیر را با نام واقعی مقصد یکسان قرار دهید و مقدار را از ورودی موردنظر نگاشت کنید. خالی‌گذاشتن این فهرست، داده کنترل فرم یا متغیر فرآیند فراخواننده را خودکار منتقل نمی‌کند.

### اندازه پاسخ و معنای موفقیت

برای کاهش جزئیات پاسخ می‌توانید `VerboseLevel` را برابر `0` قرار دهید تا نتیجه بر متغیرهای خروجی فرآیند متمرکز شود. اگر این پارامتر را نفرستید، پاسخ کامل‌تر برمی‌گردد. متغیرهای خروجی موردنیاز را در End مقصد تعریف کنید؛ کم‌کردن جزئیات پاسخ، جای تعریف خروجی را نمی‌گیرد.

شروع با Message Start، اجرای مستقل فرآیند مقصد را آغاز می‌کند. اگر فراخواننده خودش یک فرآیند باشد، ادامه آن و ادامه فرآیند مقصد را جدا بررسی کنید. برای سناریویی که فرآیند فراخواننده باید در یک فعالیت منتظر پایان فرآیند فرزند بماند و خروجی‌هایش را تحویل بگیرد، Call Activity را به‌کار ببرید.

برای کاهش جزئیات پاسخ می‌توانید `VerboseLevel` را برابر `0` قرار دهید. در این حالت محتوای نتیجه به خروجی‌های رویداد برمی‌گردد و اطلاعات عمومی وضعیت پاسخ، مانند موفقیت یا خطا، همچنان باید بررسی شود. این تنظیم داده‌ای را که هنوز تولید نشده ایجاد نمی‌کند؛ اگر مقصد در انتظار UserTask باشد، نباید نتیجه نهایی End را پیش از رسیدن به آن گام انتظار داشته باشید.

اگر `VerboseLevel` را نفرستید، پاسخ با جزئیات پیش‌فرض برمی‌گردد. ابتدا وضعیت موفقیت یا خطا را بررسی کنید و سپس عضو موردنیاز نتیجه را بخوانید. صرف دریافت یک پاسخ HTTP یا نمایش یک پیام ثابت، اثبات‌کننده دریافت درست متغیرهای مقصد نیست.

## Message Boundary؛ ادامهٔ انتظار جاری

![نماد Message Boundary Event](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=41DF7FCB-8F59-4B03-A325-4EA1B40A0B0D)

Message Boundary Event

Message Boundary امکان ادامه یک کار را از فراخوانی بیرونی فراهم می‌کند، در حالی که همان UserTask از کارتابل معمول نیز قابل انجام است. نمونه کاربرد آن کار تأیید درخواست است: مسئول می‌تواند فرم کارتابل را ثبت کند یا از یک فهرست اختصاصی درخواست‌ها، همان مورد را تأیید کند.

در این الگو یک انتظار کاری، دو راه تکمیل دارد. پس از تکمیل از یکی از راه‌ها، راه دیگر نباید دوباره همان کار را ادامه دهد. Message Boundary را از Message Start تفکیک کنید: مرزی، کار موجود را ادامه می‌دهد؛ شروع، نمونه جدید می‌سازد.

### آماده‌سازی UserTask و رویداد مرزی

1.  UserTask تأیید را در Lane مسئول مربوط قرار دهید و مسیر عادی خروجی آن را تکمیل کنید.
2.  Message Boundary را روی مرز همین UserTask قرار دهید.
3.  مسیر خروجی خود رویداد را به گام بعد از تأیید بیرونی وصل کنید؛ برای نمونه سرویس ثبت وضعیت تأیید.
4.  سرویس فراهم‌کننده داده رویداد و پارامترهای آن را تنظیم کنید.
5.  خروجی موردنیاز سرویس را در متغیر ذخیره کنید.
6.  کاربر مجاز برای ادامه بیرونی و تنظیم دسترسی مربوط را مشخص کنید.
7.  فرآیند را ذخیره کنید و هر دو راه تکمیل را با نمونه‌های جدا بررسی کنید.

رویداد پیام روی کار تأیید قرار دارد و خط خروجی مستقل آن، مسیر تکمیل بیرونی را مشخص می‌کند.

> **نکته — مسیر ادامه بیرونی:** خروجی رویداد مرزی را حتماً متصل کنید. کامل‌بودن مسیر عادی UserTask، نبودن مسیر خروجی Message Boundary را جبران نمی‌کند؛ فراخوانی بیرونی باید مقصد مشخصی برای ادامه داشته باشد.

### تنظیمات Message Boundary

در Message Boundary، منبع داده و ورودی‌ها را همراه هویت معتبر اجرای ادامه بیرونی تعیین کنید. این تنظیمات با تنظیمات آغاز یک نمونه جدید یکسان نیستند.

| گزینه | کاربرد |
| --- | --- |
| مدیریت منبع داده | انتخاب منبع داده؛ پس از انتخاب، شناسه، عنوان و نوع منبع داده در پنل دیده می‌شود. |
| مدیریت پارامترها | مقداردهی ورودی‌های منبع داده. |
| تنظیمات خروجی | بدون خروجی یا نگهداری خروجی در Variable. |
| کاربر معتبر | انتخاب هویت مجاز برای تکمیل بیرونی. |
| اعمال سطح دسترسی لین جاری | کنترل دسترسی با توجه به Lane جاری. |
| تنظیمات عنوان اختیاری | فعال‌سازی و تنظیم عنوان اختیاری نمونه. |
| تنظیمات اعلان شرح ارجاع | فعال‌سازی تنظیم مربوط به شرح ارجاع. |
| ذخیره تغییرات | ثبت تنظیمات Message Boundary. |

برای تکمیل بیرونی باید نمونه منتظر و گام صحیح آن مشخص باشند؛ شناسه Record فرم، ProcessCreationID و شناسه گام یا ارجاع را به جای یکدیگر استفاده نکنید. وقتی ادامه از یکی از مسیرهای کارتابل یا فراخوانی بیرونی انجام شد، همان انتظار نباید بار دوم ادامه پیدا کند.

### Message Boundary: ثبت انتظار در ابتدا، ادامه پس از پیام

Providerِ Message Boundary **هنگام رسیدن نمونه به User Task** اجرا می‌شود تا اطلاعات انتظار را در محل موردنیاز کسب‌وکار ثبت کند. دریافت پیام، محرک ادامهٔ بعدی است؛ اجرای Provider تا آن لحظه عقب نمی‌افتد. نوع منبع داده می‌تواند SQL، REST، WSDL یا منبع مناسب دیگری باشد. شباهت تنظیمات منبع داده با Service Task، رفتار این دو عنصر را یکسان نمی‌کند.

Provider باید دو ورودی متناظر با `@@ProcessCreationID` و `@@CurrentSteps` داشته باشد. شناسهٔ نمونه، اجرای موردنظر را مشخص می‌کند و شناسهٔ گام، محل انتظار را. در تصویر، نام پارامترهای نمونه `first` و `second` است؛ آنچه باید با قرارداد Provider هماهنگ شود مقدارهای دو شناسه است، نه کپی‌کردن این نام‌های نمونه در همهٔ منبع‌های داده.

### ثبت اطلاعات انتظار برای ادامه بیرونی

سرویس رویداد می‌تواند اطلاعات لازم برای فهرست درخواست‌های قابل اقدام را ثبت کند. برای اینکه درخواست بیرونی بداند کدام نمونه و کدام گام را ادامه دهد، شناسه نمونه و مشخصات گام جاری باید همراه رکورد درخواست نگهداری شوند.

| داده | کاربرد |
| --- | --- |
| `@@ProcessCreationID` | شناسایی نمونه فرآیندی که منتظر ادامه است |
| `@@CurrentSteps` | اطلاعات گام جاری برای اتصال درخواست بیرونی به همان انتظار |
| شناسه رکورد درخواست | ارتباط داده کسب‌وکار و ردیف فهرست اختصاصی با فرآیند |
| کاربر مجاز | تعیین هویتی که اجازه تکمیل بیرونی دارد |

دو متغیر سیستمی نمونه و گام را به ورودی‌های سرویس مربوط نگاشت کنید. شناسه جدول درخواست، شناسه نمونه فرآیند و شناسه گام یکسان نیستند؛ برای هرکدام فیلد و نگاشت جدا داشته باشید. خروجی سرویس، مانند شناسه رکورد درخواست ثبت‌شده، می‌تواند در متغیر فرآیند قرار گیرد و در ادامه استفاده شود.

در دکمه ادامه بیرونی، ابتدا احراز هویت معتبر انجام شود و سپس فراخوانی ادامه فرآیند با اطلاعات همان انتظار اجرا شود. ساخت توکن، پارامترهای ادامه و سرویس واسط با الگوی Receive Task در Taskها و Activityها مرتبط است؛ در Message Boundary، انتظار به UserTask موجود متصل است.

### ادامهٔ مجاز و رقابت با Timer Boundary

سامانهٔ فراخواننده دو شناسهٔ ذخیره‌شده را برای ادامهٔ همان انتظار، از مسیر `ContinueProcess` در سرویس عمومی یا helper مربوط به `absoluteMethodHelper` ارسال می‌کند. هویت فراخوان باید با Token یا نشست معتبر احراز شده و مطابق تنظیم «کاربر معتبر» مجاز باشد؛ داشتن شناسهٔ صحیح نمونه و گام، به‌تنهایی مجوز ادامه نمی‌دهد.

| پیام معتبر پیش از سررسید می‌رسد. | User Task از کارتابل خارج می‌شود، مسیر Message Boundary ادامه می‌یابد و Timer Boundary دیگرِ همان انتظار لغو می‌شود. |

برای آزمون، دو اجرای مستقل بسازید: در یکی پیام را پیش از موعد بفرستید و در دیگری اجازه دهید Timer زودتر فعال شود. کارتابل میزبان و تاریخچهٔ همان نمونه را بررسی کنید تا فقط مسیر مربوط به رخداد تکمیل‌کننده ادامه یافته باشد.

### Message Boundary در مدل درخواست سفارشی

در این مدل، رویداد Message Boundary به لبهٔ UserTask متصل است و مسیر خروجی آن به ServiceTask «تغییر وضعیت درخواست» می‌رود. تنظیمات `MessageEventDefinition` مدیریت منبع داده، خروجی و «کاربر معتبر» را نشان می‌دهد. این نمای طراحی، اتصال رویداد و وظیفه را روشن می‌کند؛ احراز مجوز فرستنده و رفتار پیام تکراری باید جداگانه آزمون شود.

### رفتار پس از یکی از دو روش تکمیل

اگر ادامه بیرونی موفق شود، کار معمول UserTask از کارتابل خارج می‌شود و دیگر برای ثبت دوباره در اختیار کاربر باقی نمی‌ماند. سابقه اجرا مشخص می‌کند ادامه از سرویس خارجی انجام شده است.

اگر کاربر از کارتابل معمول فرم را ثبت کند، انتظار Message Boundary همان کار نیز خاتمه می‌یابد و فراخوانی بیرونی بعدی نباید آن را دوباره ادامه دهد. در فهرست اختصاصی نیز وضعیت رکورد درخواست را با سرویس بعد از تأیید به‌روز کنید تا درخواست انجام‌شده همچنان در فهرست «در انتظار» نمایش داده نشود.

برای نمونه، اگر فهرست فقط رکوردهای تأییدنشده را نشان می‌دهد، سرویس ادامه باید وضعیت تأیید رکورد را ثبت کند. خارج‌شدن از کارتابل فرآیند، به‌تنهایی شرط فیلتر جدول اختصاصی شما را تغییر نمی‌دهد.

### ترتیب عملیات در End Throw Signal

**End Throw Signal** ابتدا عملیات Throw Signal را انجام می‌دهد و سپس رفتار End عادی را اجرا می‌کند: تولید متغیرهای خروجی و، هنگام تحقق پایان واقعیِ نمونه و باقی‌نماندن ارجاع منتظر، ثبت پایان رسمی. رسیدن یک شاخه به End در حضور انتظار فعالِ شاخهٔ دیگر، به‌تنهایی پایان کل نمونه نیست. بنابراین تنظیم Signal جای تنظیم خروجی End را نمی‌گیرد. در مدل داده، پایان رسمی با وضعیت `IsFinish` در `dbo.ProcessCreation` منعکس می‌شود؛ شرح و خروجی آخرین Node به‌تنهایی جای بررسی وضعیت نمونه را نمی‌گیرد.

## رفتار اجرا، دسترسی و دادهٔ Signal

Signal یک ارتباط چندبه‌چند است. یک Throw می‌تواند هم‌زمان برای Start Catchهای چند Process نمونه جدید بسازد و چند ProcessCreation را که از قبل در Intermediate Catch منتظرند ادامه دهد. چند Throw در یک Process یا Processهای مختلف نیز می‌توانند از یک کلید مشترک استفاده کنند.

دریافت سیگنال دو شرط دارد: کلید فرستنده و گیرنده یکسان باشد و دسترسی Lane گیرنده شامل دسترسی فرستنده باشد. جهت این رابطه مهم است: دسترسی Lane حاوی Throw باید زیرمجموعه دسترسی Laneهای Catch باشد. برای نمونه، کاربری که User Task پیش از Throw را ادامه داده باید در Lane گیرنده نیز دسترسی داشته باشد.

در Throw، کلید را تایپ می‌کنید؛ در Catch، آن را از فهرست کلیدهای تعریف‌شده برمی‌گزینید. اگر کلید در فهرست دیده نمی‌شود، وجود Throw متناظر و ذخیره‌شدن Processی را بررسی کنید که آن Throw را تعریف کرده است. کلیدِ Throw در Process ذخیره‌نشده هنوز برای انتخاب گیرنده آماده نیست.

گیرنده می‌تواند در همان ProcessCreation جاری باشد. برای مثال، یک شاخه موازی به Intermediate Catch رسیده و منتظر است؛ اجرای Throw در شاخه دیگر می‌تواند همان انتظار را آزاد کند. Intermediate Catch در این حالت نیز Creation تازه نمی‌سازد.

ورودی‌های سیگنال براساس نام Variable مقصد نگاشت می‌شوند. یک نام ممکن است فقط در بعضی گیرندگان وجود داشته باشد؛ مقدار برای مقصدی اعمال می‌شود که Variable هم‌نام را دارد. برای شناسایی فرستنده می‌توانید، برای مثال، ProcessCreationID جاری را به Variable مقصد با نام SourceCreationID بدهید. Start Catch این مقدار را هنگام ساخت نمونه می‌گیرد و Intermediate Catch آن را در نمونه موجود، پیش از ادامه مسیر، دریافت می‌کند.

اجرای Throw به‌صورت Async و Fire-and-forget است: فرستنده منتظر پایان هیچ‌یک از Processهای دریافت‌کننده نمی‌ماند. Intermediate Throw پس از انتشار، مسیر خودش را ادامه می‌دهد؛ Signal End Event پس از انتشار، رفتار پایان Process را اجرا می‌کند. این تفاوت را هنگام انتخاب Event و مقایسه آن با Call Activity در نظر بگیرید.

## End Event؛ پایان مسیر و خروجی نهایی

![نماد End Event](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=2B940854-63A1-4C68-8B63-A9D4F9C62AAB)

End Event

End را به آخرین گام مسیر وصل کنید. در فرآیند دارای تصمیم، ممکن است مسیرهای تأیید و عدم تأیید پایان‌های متفاوتی داشته باشند. عنوان پایان را متناسب با نتیجه بنویسید تا تشخیص آن در نمودار آسان باشد.

اگر چند شاخه هم‌زمان دارید و پایان باید بعد از انجام همه کارها باشد، پیش از End جمع‌کننده مناسب قرار دهید. صرف رساندن یکی از شاخه‌ها به End، طراحی هماهنگی شاخه‌های دیگر را انجام نمی‌دهد. انتخاب و تنظیم جمع‌کننده در Gatewayها توضیح داده شده است.

### تعریف متغیرهای خروجی در End

وقتی فرآیند باید نتیجه‌ای را به فراخواننده برگرداند، خروجی را در End تعریف کنید. این خروجی، قرارداد نتیجه فرآیند است؛ برای نمونه وضعیت پذیرفته‌شدن درخواست یا عنوانی که هنگام اجرای فرآیند ساخته شده است.

1.  End را انتخاب کنید و **مدیریت متغیرهای خروجی** را باز کنید.
2.  **افزودن/ویرایش متغیر** را انتخاب کنید.
3.  نام کلید خروجی را تعیین کنید؛ فراخواننده همین نام را بر��ی دریافت نتیجه به‌کار می‌برد.
4.  نوع مقداردهی و مقدار خروجی را مشخص کنید. خروجی می‌تواند یک مقدار ثابت یا مقدار متغیر فرآیند باشد.
5.  ردیف‌های لازم را اضافه و تغییرات را ذخیره کنید.
6.  برای هر مسیری که پایان و نتیجه متفاوت دارد، تنظیم End همان مسیر را بررسی کنید.

[![مدیریت متغیرهای خروجی End با مقدار ثابت و مقدار متغیر](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=7486FBE7-EEC5-4794-99DB-488FD365136D)](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=7486FBE7-EEC5-4794-99DB-488FD365136D "بازکردن تصویر در اندازه اصلی")

خروجی IsOk مقدار ثابت ۱ دارد و CreatedCustomTitle از متغیر @@CustomTitle مقدار می‌گیرد. این نام‌ها نمونه قرارداد خروجی هستند و باید با دریافت‌کننده نتیجه هماهنگ باشند.

در Call Activity، دو تنظیم جدا لازم است: End فرآیند مقصد کلیدها و مقادیر خروجی را تعیین می‌کند؛ Call Activity در فرآیند فراخواننده مشخص می‌کند هر کلید در کدام متغیر خودش ذخیره شود. تعریف یکی جای دیگری را نمی‌گیرد. چرخه کامل ورودی، انتظار برای فرآیند مقصد و دریافت نتیجه در Taskها و Activityها آمده است.

### End Event و قرارداد Variableهای خروجی

برای دریافت نتیجه از Process، End Event مسیر نهایی را انتخاب و «مدیریت متغیرهای خروجی» را باز کنید. نام کلید خروجی قرارداد دریافت نتیجه است؛ برای یکپارچگی یا Call Activity، نام کلید و روش نگاشت آن باید در هر دو طرف یکسان باشد.

[![مدیریت Variableهای خروجی در End Event](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=EE1D9A09-0AD3-4A6D-81AA-A78D7EB71677)](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=EE1D9A09-0AD3-4A6D-81AA-A78D7EB71677 "بازکردن تصویر در اندازه اصلی")

مدیریت Variableهای خروجی در End Event

1.  دکمه «افزودن/ویرایش متغیر» را انتخاب کنید.
2.  نام کلید خروجی را تعیین کنید.
3.  نوع ورودی را از مقدار ثابت، بدون مقدار، متغیر یا تابع انتخاب کنید.
4.  مقدار یا مسیر داده متناظر را کامل کنید.
5.  برای کلیدهای دیگر همین مراحل را تکرار و «ذخیره و بستن» را اجرا کنید.

جدول امکان جستجوی کل جدول، فیلتر ستون‌ها و صفحه‌بندی دارد. ستون‌های «نام کلید»، «نوع ورودی» و «مقدار ورودی» برای بازبینی قرارداد خروجی کنار هم نمایش داده می‌شوند. تابعی مانند Concat می‌تواند مقدار خروجی را از چند جزء بسازد؛ خواندن Variable نیز می‌تواند داده ServiceData را به خروجی متصل کند.

در Process دارای چند مسیر پایان، خروجی همان End که مسیر به آن رسیده است اهمیت دارد. در Call Activity، Process فرزند باید به پایان برسد تا Process پدر از فعالیت فراخوانی عبور کند؛ نگاشت خروجی‌های فرزند در تنظیم Call Activity پدر تکمیل می‌شود.

### یک قرارداد خروجی روشن در End

متغیرهای خروجی End، نتیجه‌ای را تعریف می‌کنند که مصرف‌کنندهٔ فرآیند دریافت می‌کند. مدل فرآیند می‌تواند چند End داشته باشد، اما اگر شاخه‌ها خروجی‌هایی با نام یا شکل متفاوت بسازند، فراخواننده دیگر یک قرارداد ثابت ندارد. برای فرآیندی که از سرویس یا کد backend شروع و همان‌جا کامل می‌شود، شاخه‌های پایانی را با Sequence Flow به **یک End مشترک** برسانید و خروجی را همان‌جا تعریف کنید.

این طراحی در کاربرد Process به‌عنوان **ESB** الزام دارد؛ فرآیند ESB را با یک End واحد تنظیم کنید. در سایر مدل‌ها، یک End توصیه‌ای برای یکنواختی نتیجه و نگه‌داری ساده‌تر است و نباید آن را ممنوعیت عمومی چند End در همهٔ فرآیندها تلقی کرد.

### چهار روش ساخت Property خروجی

در «مدیریت متغیرهای خروجی»، برای هر Property یک نام کلید و روش مقداردهی تعیین کنید. نام کلید، نام نتیجه‌ای است که مصرف‌کننده می‌بیند؛ لازم نیست با نام Variable داخلی یکی باشد. مقدار می‌تواند ثابت، بدون مقدار، انتخاب‌شده از Variable یا حاصل تابع باشد.

[![چهار خروجی نمونه: مقدار ثابت، بدون مقدار، دادهٔ Variable و نتیجهٔ تابع Concat.](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=57578426-C72C-450D-B235-9822E8756E79)](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=57578426-C72C-450D-B235-9822E8756E79 "بازکردن تصویر در اندازه اصلی")

چهار خروجی نمونه: مقدار ثابت، بدون مقدار، دادهٔ Variable و نتیجهٔ تابع Concat.

| کلید نمونه | روش مقداردهی | مقدار نمایش‌داده‌شده |
| --- | --- | --- |
| `OutPutOfThisProcessNumber_1` | مقدار ثابت | `some constant value` |
| `OutPutOfThisProcessNumber_2` | بدون مقدار | `none` در جدول تنظیمات |
| `OutPutOfThisProcessNumber_3` | متغیر | `@@perm:ServiceData` |
| `OutPutOfThisProcessNumber_4` | تابع | ترکیب پیشوند `Bearer` با `@perm:ServiceData[0]['Token']` توسط `Concat` |

این مقادیر مثال‌اند. برای تنظیم واقعی، نام Variable و مسیر Property را با دادهٔ موجود در اجرای خود تطبیق دهید. عبارت «بدون مقدار» را با رشتهٔ دلخواه `"none"` در کد فراخواننده یکی نگیرید؛ جدول تنظیمات نمایش رابط است و شکل نهایی پاسخ به قرارداد API و سطح خروجی انتخاب‌شده نیز بستگی دارد.

اگر نتیجه ساختاریافته لازم دارید، کل دادهٔ Variable را انتخاب کنید؛ اگر فقط یک Token یا شناسه لازم است، مسیر همان Property را بخوانید. خروجی پایان فرآیند می‌تواند در دکمهٔ Form یا Custom JS مصرف و در Field یا SubForm مقصد قرار گیرد. تنظیم خروجی به‌تنهایی این داده را در Form مقصد نمی‌نویسد؛ نگاشت مصرف‌کننده باید جداگانه تعریف شود.

## Error Boundary؛ هدایت خطای فعالیت

![نماد Error Boundary Event](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=C4E9C2D6-AC48-4F72-A5C1-8B1458B1FECC)

Error Boundary Event

Error Boundary برای طراحی واکنش به خطای فعالیت میزبان به‌کار می‌رود. برای نمونه، اگر ServiceTask یا ScriptTask در اجرا خطا داد، به جای ادامه عادی، اطلاعات خطا در متغیر ذخیره شود و یک کار رسیدگی به مسئول مربوط برسد.

این رویداد روی مرز فعالیت قرار می‌گیرد. خطای فعالیت میزبان محرک آن است؛ برای شروع مسیر مرزی لازم نیست یک Checkbox یا شرط Gateway را فعال کنید.

### میزبان‌های مجاز Error Boundary

Error Boundary روی User Task به کار نمی‌رود؛ برای رسیدگی به استثنای فعالیت‌های خودکار، مانند Service Task، Script Task، Business Rule Task و Call Activity، کاربرد دارد.

### تمایز خطای Form با خطای موتور Process

در سناریوی User Task، Timer و Message برای پایان مهلت یا ادامه از بیرون مطرح‌اند. خطاهای کنترل یا ثبت Form را با خطاهای موتور Process که به Error Boundary مربوط‌اند یکسان نگیرید.

### تنظیم مسیر خطا

1.  Error Boundary را روی مرز فعالیتی که خطای آن باید رسیدگی شود قرار دهید.
2.  از رویداد یک مسیر خروجی به گام رسیدگی رسم کنید؛ مانند UserTask نمایش و بررسی خطا.
3.  متغیری برای نگهداری اطلاعات خطا بسازید.
4.  در تنظیمات Error Boundary، همان متغیر را به‌عنوان محل ذخیره خروجی انتخاب کنید.
5.  در صورت نیاز شرح ارجاع سفارشی بنویسید تا دریافت‌کننده علت ارجاع را بداند.
6.  فرم و دریافت‌کننده گام رسیدگی را تکمیل کنید.
7.  مسیر عادی فعالیت را نیز کامل نگه دارید تا در اجرای موفق ادامه عادی انجام شود.

رویداد خطا روی لبه ServiceTask قرار می‌گیرد؛ مسیر عادی سرویس نیز به پایان متصل است.

متغیر خروجی را پیش از استفاده در فرم رسیدگی مشخص کنید؛ شرح ارجاع، متن همراه کار را تعیین می‌کند.

### Error Boundary؛ ذخیره اطلاعات خطا و شرح ارجاع

Error Boundary را به فعالیتی متصل کنید که خطای آن باید به مسیر رسیدگی منتقل شود. در فیلد «ذخیره خطا در...» Variable مقصد خطا را انتخاب کنید. در صورت نیاز «استفاده از شرح ارجاع سفارشی» را فعال کنید و پس از تنظیم، «ذخیره تنظیمات» را بزنید.

ذخیره خطا در Variable منتخب و تنظیم شرح ارجاع

متغیر خطا باید همان Variableای باشد که گام رسیدگی از آن می‌خواند. اطلاعات خطا می‌تواند شامل پیام، نوع و محل وقوع باشد؛ برای نمایش در Form، منبع ServiceData و مسیر موردنیاز را تعیین کنید. خروجی خالی مجاز در Service Task یا Script Task را با استثنای اجرا یکسان ندانید: وقتی خروجی Null مجاز است، نبودن داده به‌تنهایی شرط ورود به مسیر خطا نیست.

### نگه‌داری دادهٔ استثنا برای رسیدگی بعدی

**نیازمند تأیید فنی:** پشتیبانی اجرایی Error Boundary روی Receive Task باید تأیید شود؛ آن را از فهرست میزبان‌های قطعی Service Task، Script Task، Business Rule Task و Call Activity نتیجه نگیرید.

Error Boundary به استثنای فعالیت میزبان واکنش نشان می‌دهد و مانند مسیر Catch برای آن عمل می‌کند. در بخش **«ذخیره خطا در...»** Variable مقصد را انتخاب کنید تا اطلاعات خطا در گام رسیدگی مصرف شود. انتخاب Variable، اتصال مسیر خروجی مرزی را بی‌نیاز نمی‌کند؛ فرم رسیدگی یا سرویس ثبت گزارش باید در همان مسیر قرار بگیرد.

**«استفاده از شرح ارجاع سفارشی»** برای متن شرح مسیر است و از دادهٔ ساختاریافتهٔ خطا مستقل است. عنوان یا شرحی با واژهٔ «خطا» به‌تنهایی استثنا ایجاد نمی‌کند؛ نتیجهٔ رد کسب‌وکار را با وقوع Exception فنی یکی نگیرید.

### استفاده از اطلاعات خطا

خروجی خطا یک متن ساده منفرد نیست؛ اطلاعاتی مانند پیام خطا، نوع خطا و محل وقوع آن در ساختار داده ذخیره می‌شود. برای نمایش آن در فرم رسیدگی، ورودی کنترل را از متغیر خطا و داده سرویس تنظیم کنید. با انتخاب همه داده‌ها می‌توانید مجموعه اطلاعات خطا را برای بررسی دریافت کنید؛ برای نمایش محدودتر، عضو موردنیاز را از همان ساختار انتخاب کنید.

نام متغیر خطا را با متغیر خروجی موفق سرویس اشتباه نگیرید. اگر فرم رسیدگی خالی است، نخست بررسی کنید متغیر انتخاب‌شده در Error Boundary همان متغیری باشد که ورودی فرم از آن می‌خواند و مسیر عضو داده درست تنظیم شده باشد.

### نمایش دادهٔ خطا در مسیر رسیدگی

در یک مسیر رسیدگی به خطا، دادهٔ خطا را می‌توان در خروجی تعیین‌شده و سپس در فرم مرحلهٔ بعد بررسی کرد. نمونهٔ نمایش‌شده بخشی از `Exception@@` را با `ExceptionType` و `ExceptionMessage` در فیلد متنی دارد. متن پیام «داده‌های خروجی سرویس نامعتبر است» و نوع `InvalidOperationException` دیده می‌شود. مقدار فیلد به‌صورت افقی بریده است؛ این نما قرارداد کامل JSON خطا را مشخص نمی‌کند.

[![نمایش بخشی از دادهٔ خطا در فیلد فرمِ مسیر رسیدگی به خطا؛ متن JSON شامل ExceptionType و ExceptionMessage.](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=A0F55E72-D3AB-4D4A-BDE5-F4286BA8D55B)](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=A0F55E72-D3AB-4D4A-BDE5-F4286BA8D55B "بازکردن تصویر در اندازه اصلی")

### تفاوت خروجی خالی مجاز با خطای اجرا

تنظیم **مجاز بودن خروجی Null** در ServiceTask بر تفسیر نتیجه خالی اثر دارد. اگر خروجی خالی سرویس را مجاز کرده باشید، خالی‌بودن داده به‌تنهایی باعث ورود به Error Boundary نمی‌شود. اما وقوع استثنا در اجرای سرویس یا اسکریپت همچنان خطا است و می‌تواند مسیر مرزی را فعال کند.

گزینه **مجاز بودن خروجی Null** در تنظیمات ScriptTask نیز وجود دارد. تنظیم و مصرف خروجی اسکریپت را همراه جزئیات Taskها و Activityها بررسی کنید.

ابتدا تعیین کنید نبودن داده در فرآیند شما نتیجه معتبر است یا وضعیت خطا. سپس تنظیم خروجی خالی و مسیر Error Boundary را هماهنگ کنید. انتظار برای ورود به مسیر خطا، در حالی که همان وضعیت را خروجی خالی مجاز اعلام کرده‌اید، طراحی متناقضی ایجاد می‌کند. جزئیات تنظیم خروجی Task در Taskها و Activityها آمده است.

برای مشاهده سابقه ارجاع و مسیر ادامه، کارتابل سوابق را بررسی کنید. فرم رسیدگی به خطا نیز باید اطلاعات ثبت‌شده در متغیر Error Boundary را در اختیار مسئول مربوط قرار دهد.

پس از تعیین گیرندگان، تب محتوای اطلاع‌رسانی را تکمیل کنید. موضوع، آدرس URL و بدنه، دادهٔ اعلان را می‌سازند. کنترل مقداردهی امکان مقدار خالی، ثابت، Variable با حالت ساده/پیشرفته/همهٔ داده‌ها و تابع را ارائه می‌کند؛ خروجی انتخاب‌شده باید با مصرف همان فیلد سازگار باشد. در نمونه، موضوع از فیلد فرمِ Variable به نام `perm` خوانده شده است:

پیش‌نمایش مسیر را بررسی کنید. نام فیلد باید با دادهٔ واقعی Variable یکسان باشد. در قسمت روش اطلاع‌رسانی، **اعلان پورتال** و **اعلان سیستم‌عامل** را مطابق نیاز انتخاب کنید؛ نمونهٔ تصویر هر دو را فعال کرده است.

برای مثال تصویر، موضوع `s1` و بدنه متن ثابت‌اند؛ URL از نخستین سطر ServiceData گرفته می‌شود:

### پارامترهای Portal در نمونهٔ پیشرفته

کارت Portal در تصویر چهار پارامتر پویا دارد. نام‌های فنی زیر به همین نمونه مربوط‌اند؛ برای رویهٔ دیگر، فهرست پارامترهای تعریف‌شدهٔ خود آن رویه را مبنا قرار دهید.

| پارامتر | مقداردهی و کاربرد نمونه |
| --- | --- |
| `RecipientUserId` | شناسه‌های کاربران مقصد به‌صورت رشته با جداکنندهٔ کاما؛ از فیلد متغیر زیر خوانده می‌شود. |
| `Icon` | نشانی فایل آیکن در Archive؛ مانند `/Archive/GetFile?id=<archive-file-id>` با شناسهٔ فایل معتبر همان محیط. |
| `RecipientRoleId` | شناسه‌های نقش‌های مقصد به‌صورت رشته با جداکنندهٔ کاما؛ مشابه ورودی کاربران. |
| `NotificationGroupId` | در آموزش می‌تواند خالی باشد یا شناسهٔ گروه تعریف‌شده در ماژول اطلاع‌رسانی را بگیرد. عدد `5` در تصویر فقط یک نمونه است. |

```
RecipientUserId:
@@perm:ServiceData[0]['UsersIdsCommaBasedConcatinatedField']

RecipientRoleId:
@@perm:ServiceData[0]['RolesIdsCommaBasedConcatinatedField']
```

نام‌های `UsersIdsCommaBasedConcatinatedField` و `RolesIdsCommaBasedConcatinatedField` نام فیلدهای نمونه‌اند؛ املای فنی فیلد موجود در خروجی خودتان را دقیق استفاده کنید. در این مثال محتوا یک رشتهٔ شناسه‌هاست، نه نام نمایشی کاربران یا عنوان نقش‌ها. شناسهٔ فایل آیکن و شناسهٔ گروه را نیز از همان محیط مقصد بردارید.

### چند رویه در یک Notification Event

در سربرگ هر کارت، نماد سطل زباله برای حذف پیکربندی و پیکان باز و بسته‌کردن جزئیات دیده می‌شود. این کنترل‌ها به همان کارت مربوط‌اند؛ علامت بستنِ بالای پنجره، کنترل جداگانهٔ صفحهٔ تنظیمات است.

با **افزودن پیکربندی جدید** می‌توانید در یک Event چند کارت ارسال داشته باشید؛ برای مثال یک کارت Portal، یک کارت OS و یک کارت برای رویهٔ سفارشی. هر کارت رویه و پارامترهای پویای خودش را دارد. پیکربندی را به یک رویه محدود فرض نکنید و مقدارهای گیرنده و سایر ورودی‌های هر کارت را جدا تکمیل کنید.

پیش از ذخیره، هر کارت را مرور کنید: رویهٔ صحیح انتخاب شده باشد، پارامترهای پویا با نوع دادهٔ مورد انتظار سازگار باشند، گیرندگان از مسیر درست خوانده شوند و مقدار URL و Icon به مقصد معتبر اشاره کند. تعریف و مدیریت داخلی رویه‌ها و گروه‌های اعلان در ماژول اطلاع‌رسانی انجام می‌شود؛ این Event محل مصرف آن‌ها در اجرای Process است.

## Graph Mobile Start؛ آغاز با ارسال دادهٔ همراه

![نماد Graph Mobile Start Event](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=628D9FB9-2E80-436B-A2CA-A634BB5A8006)

Graph Mobile Start Event

Graph Mobile Start دریافت داده یک کار همراه نامحدود را به آغاز فرآیند وصل می‌کند. برای نمونه، کاربر همراه فرم مأموریت را تکمیل می‌کند و پس از ارسال رکورد به سرور، فرآیند بررسی همان مأموریت آغاز می‌شود.

### پیش‌نیاز و انتخاب کار همراه

پیش از تنظیم رویداد، کار همراه نامحدود موردنظر را در مدیریت کار آماده کنید. فرم، دریافت‌کنندگان و تنظیمات لازم آن باید آماده باشند تا کاربران بتوانند رکورد را در همراه تکمیل و ارسال کنند. فهرست این رویداد برای انتخاب کار همراه نامحدود است؛ یک کار محدود را به جای آن در نظر نگیرید.

1.  Start را به نوع Graph Mobile Start تغییر دهید.
2.  در پنل رویداد، **لیست وظایف همراه نامحدود** را باز کنید.
3.  کار همراهی را که داده آن باید فرآیند را آغاز کند انتخاب کنید.
4.  Start را به گام دریافت و پردازش داده متصل کنید؛ برای نمونه یک ServiceTask.
5.  ادامه مسیر، کارهای انسانی و پایان را تنظیم کنید.
6.  فرآیند را ذخیره و نسخه موردنظر را فعال کنید.

[![انتخاب وظیفه همراه نامحدود در تنظیم Graph Mobile Start](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=270C3B39-77C8-4A7C-925B-2A0FD5E31384)](https://portal.graphbpms.ir/Archive/GetFileAnonymous?id=270C3B39-77C8-4A7C-925B-2A0FD5E31384 "بازکردن تصویر در اندازه اصلی")

ارتباط شروع موبایلی با انتخاب کار همراه نامحدود برقرار می‌شود.

### Graph Mobile Start؛ از Task نامحدود تا ارسال به سرور

Graph Mobile Start یک Node اختصاصی GraphBPMS است که بر پایهٔ Start Event، ماژول برداشت اطلاعات میدانی را به Process متصل می‌کند. داده ارسالی یک وظیفه همراه نامحدود از این ورودی آغاز Process را ایجاد می‌کند. پیش از تنظیم رویداد، Task مربوط را از مسیر «برداشت اطلاعات میدانی ← مدیریت کار» آماده کنید؛ نوع وظیفه باید «نامحدود» باشد.

دسترسی به ارسال به سرور از منوی Task در PWA

داده آغاز از Variable سیستمی «داده‌های ارسالی از طریق شروع موبایلی» با نام MobileRecordData قابل دریافت است. این داده از جنس ServiceData است و می‌تواند لیست رکوردهای ارسالی Task را در خود داشته باشد؛ آن را FormData تک‌رکوردی فرض نکنید. در گام بعدی، برای مصرف کل رکورد از همه داده‌ها و برای یک فیلد از مسیر عضو ServiceData استفاده کنید. انتخاب Event به‌تنهایی عملیات ذخیره‌سازی یا پردازش دلخواه را انجام نمی‌دهد؛ آن منطق را در گام بعدی Process تنظیم کنید.

در یک نمونهٔ کاربرد، مسئول جمع‌آوری کالاهای تحویل‌گرفته‌شده یا بازنگشته، طی روز رکوردهای متعددی را با گوشی ثبت می‌کند. Task نامحدود برای این ثبت‌های پی‌درپی مناسب است؛ رکوردهای ارسال‌شده به سرور وارد Process مرتبط می‌شوند.

همان مجوزهای کاربر و نقشِ Task تعیین می‌کنند کار در PWA یا APK برای چه کاربرانی نمایش داده شود.

### دریافت داده ارسالی در فرآیند

داده شروع موبایلی از متغیر سیستمی **داده‌های ارسالی از طریق شروع موبایلی** در دسترس است. در تنظیم ورودی ServiceTask، این متغیر را انتخاب کنید و در حالت پیشرفته از `ServiceData` و عضو موردنظر یا همه داده‌ها استفاده کنید.

اگر سرویس باید کل رکورد همراه را پردازش کند، همه داده‌ها را بدهید. اگر تنها یک مقدار لازم است، مسیر همان فیلد را انتخاب کنید. متغیر سیستمی را با یک متغیر دستی هم‌نام جایگزین نکنید؛ داده آغاز، از ارسال همراه تأمین می‌شود.

ثبت لاگ یا ذخیره داده در جدول به رفتار سرویس بعدی وابسته است. انتخاب Graph Mobile Start به‌تنهایی به معنی اجرای هر عملیات ذخیره‌سازی دلخواه نیست؛ ServiceTask باید همان عملیات موردنیاز شما را انجام دهد.

### ساختار داده شروع موبایلی

پس از ارسال Task همراه به سرور و آغاز Process، داده‌ها در Variable سیستمی `@@MobileRecordData` با عنوان «داده‌های ارسالی از طریق شروع موبایلی» در دسترس‌اند. با هر ارسال به سرور، برای هر Process متصل به Task یک نمونه آغاز می‌شود و تمام رکوردهای همان ارسال در همان نمونه قرار می‌گیرند. این داده از جنس `ServiceData` است و لیست رکوردهای ارسالی را نگه می‌دارد. آن را FormData تک‌رکوردی فرض نکنید؛ برای خواندن داده، نوع منبع و در صورت نیاز Index و مسیر عضو را متناسب با ServiceData تنظیم کنید.

### زمان ایجاد نمونه و ارسال چند رکورد

ذخیره محلی فرم در همراه، به‌تنهایی نمونه فرآیند را آغاز نمی‌کند. محرک شروع، **ارسال به سرور** است. بنابراین پس از تکمیل فرم، ارسال موفق به سرور را بررسی کنید و سپس نمونه ایجادشده و کارتابل مقصد را ببینید.

> در ارسال گروهی همراه، دادهٔ آغاز در `@@MobileRecordData` با ساختار ServiceData و به‌صورت فهرست رکوردهای ارسالی در دسترس است. برای خواندن همهٔ رکوردها از کل ServiceData و برای عضو مشخص از Index و مسیر مناسب استفاده کنید. برای هر Process متصل، هر ارسال یک ProcessCreation ایجاد می‌کند و کل رکوردهای همان ارسال در همان نمونه می‌آیند. این رفتار با ایجاد یک نمونهٔ جدا برای ��ر رکورد تفاوت دارد.

شروع موبایلی برای دریافت این ارسال تنظیم می‌شود؛ آغاز آن را از فهرست شروع عادی کاربر دنبال نکنید. اگر بعد از ارسال باید یک UserTask به مسئول بررسی برسد، دسترسی Lane مقصد را مستقل از رویداد شروع مشخص کنید.

## بررسی نتیجه و رفع اشکال

پس از ذخیره مدل، برای هر محرک یک نمونه واقعی بررسی کنید. در تایمر مرزی، یک بار پیش از موعد اقدام کنید و یک بار اجازه دهید مهلت تمام شود. در Message Boundary، ادامه عادی و بیرونی را روی نمونه‌های جدا انجام دهید. در شروع موبایلی، ذخیره محلی را از ارسال به سرور جدا ببینید.

| نشانه | بررسی لازم |
| --- | --- |
| Timer Start نمونه ایجاد نمی‌کند | فعال‌بودن موتور، حساب اجرا، آدرس پایه، شروع تایمر همان نسخه، تقویم و موعد ثبت‌شده |
| پس از تغییر تنظیمات تایمر رفتار قبلی ادامه دارد | بارگذاری تنظیمات جدید با راه‌اندازی مجدد برنامه |
| کار بعد از تایمر در کارتابل فرد موردنظر نیست | Lane مقصد، هویت اجرای سیستمی و محاسبه گیرنده از درخواست‌کننده واقعی |
| موعد متغیری اجرا نمی‌شود | مقدار واقعی تاریخ و ساعت و مسیر عضو متغیر حاوی موعد |
| کار قبل از رسیدن به تأییدکننده باید تأخیر داشته باشد | استفاده از Timer میانی پیش از UserTask؛ Timer Boundary مهلت پس از ایجاد کار است |
| پس از اتمام مهلت به مقصد نمی‌رسد | اتصال واقعی Boundary به میزبان، خط خروجی رویداد و تنظیمات کار مقصد |
| خروجی خالی سرویس وارد Error Boundary نمی‌شود | **مجاز بودن خروجی Null** در ServiceTask و تفاوت آن با استثنای اجرای فعالیت |
| فرم رسیدگی به خطا خالی است | متغیر خروجی Error Boundary و مسیر خواندن ساختار داده خطا |
| فرم همراه ذخیره شده، اما نمونه‌ای ایجاد نشده | ارسال موفق به سرور و انتخاب کار همراه نامحدود صحیح |
| درخواست بیرونی نمی‌تواند کار منتظر را ادامه دهد | نمونه و گام صحیح، وضعیت انجام‌نشدن انتظار، کاربر مجاز و توکن معتبر |
| شروع سرویس موفق است، اما فرم بعدی باز نمی‌شود | انتخاب **به صورت سرویس**؛ برای نمایش ادامه، نحوه شروع معمولی را بررسی کنید |
| متغیر ورودی مقصد خالی است | فهرست `Variables`، نام دقیق متغیر و نگاشت مقدار در فراخواننده |
| خروجی نهایی فراخوانی هنوز موجود نیست | رسیدن واقعی مسیر مقصد به End و تعریف خروجی در همان End |

برای دنبال‌کردن تاریخچه ارجاع‌ها و مسیر انجام‌شده، کارتابل سوابق را باز کنید؛ وصول کار بعدی را در کارتابل ورودی بررسی کنید.
