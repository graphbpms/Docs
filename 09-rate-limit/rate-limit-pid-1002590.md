## 1. صفحه تنظیمات سیستم

تنظیمات سیستم فهرستی از تنظیمات کلید-مقدار سامانه است و از مسیر زیر باز می‌شود:

```
منو ← پیکربندی سیستم ← تنظیمات سیستم

```

هر ردیف این صفحه یک تنظیم است و ستون‌های زیر را دارد:

ستون
کاربرد

نام تنظیم
کلید تنظیم

مقدار تنظیم
مقدار تنظیم

توضیحات
شرح کاربرد تنظیم

فعال
وضعیت فعال یا غیرفعال بودن تنظیم

اطلاعات تکمیلی
توضیحات تکمیلی درباره مقادیر مجاز تنظیم

با دکمه «افزودن تنظیمات» می‌توان تنظیم جدید ایجاد کرد و با کادرهای جستجو در بالای هر ستون، تنظیم مورد نظر را پیدا کرد. در این آموزش، تنظیم مربوط به Rate Limit با نام `RateLimitEndpoints` توضیح داده می‌شود.

## 2. Rate Limit چیست و چه کاربردی دارد؟

محدودیت نرخ درخواست (Rate Limiting) تعداد درخواست‌های مجاز یک کلاینت به یک Endpoint را در یک بازه زمانی مشخص محدود می‌کند. با آن در برابر موارد زیر محافظت می‌شود:

- حملات منع سرویس (DoS/DDoS)

- حملات حدس کلمه عبور (Brute-Force)

- فراخوانی‌های مکرر و معیوب ناشی از لوپ در کد کلاینت‌ها

- اشباع منابع سرور (Thread Pool و Connection Pool)

سیستم Rate Limit در لایه Middleware خط‌لوله اجرایی برنامه قرار دارد و هر درخواست را پیش از ورود به اکشن‌ها و کنترلرهای BPMS بررسی می‌کند:

```
درخواست ورودی
   ↓
وجود قانون برای مسیر؟
   ├─ خیر ← عبور مستقیم به کنترلر
   └─ بله ← تطبیق Method و ارزیابی شروط (Condition)
              ↓
          تشخیص هویت کلاینت (IP یا UserId)
              ↓
          افزایش شمارنده در پنجره زمانی
              ├─ سهمیه مجاز ← عبور درخواست + هدرهای X-RateLimit-*
              └─ سهمیه تمام‌شده ← پاسخ 429 بدون ورود به BPMS

```

تنظیمات Rate Limit در سامانه از چهار محل قابل پیکربندی است که یکی از آن‌ها همین صفحه تنظیمات سیستم است. مزیت اصلی این روش، اعمال زنده تغییرات بدون ریست سرور است.

## 3. تنظیم Rate Limit در تنظیمات سیستم

قوانین Rate Limit در تنظیمی با نام `RateLimitEndpoints` نگهداری می‌شوند. مقدار این تنظیم یک آرایه از آبجکت‌های JSON است که هر آبجکت یک قانون است. برای تنظیم:

- از مسیر **منو ← پیکربندی سیستم ← تنظیمات سیستم** صفحه تنظیمات را باز کنید.

- در ستون «نام تنظیم» عبارت `RateLimitEndpoints` را جستجو کنید.

- اگر تنظیم وجود دارد، آن را برای ویرایش باز کنید. اگر وجود ندارد، با «افزودن تنظیمات» آن را بسازید و نام تنظیم را `RateLimitEndpoints` بنویسید.

- در «مقدار تنظیم»، قوانین را به‌صورت آرایه JSON وارد کنید.

- تنظیم را ذخیره کنید. تغییر بدون ریست سرور و به‌صورت زنده اعمال می‌شود.

نمونه مقدار تنظیم با دو قانون:

```
[
  {
    "Name": "Login_Auth_Rule",
    "Path": "/Login/Authenticate",
    "HttpMethod": "POST",
    "Limit": 5,
    "WindowInSeconds": 60,
    "LimitByUser": false,
    "Message": "تعداد تلاش‌های ورود بیش از حد مجاز است. لطفاً {0} ثانیه دیگر تلاش فرمایید.",
    "IsActive": true
  },
  {
    "Name": "Process_Run_User",
    "Path": "/Process/RunProcess",
    "Limit": 30,
    "WindowInSeconds": 60,
    "LimitByUser": true,
    "IsActive": true
  }
]

```

## 4. ساختار قانون و خصوصیات آن

هر قانون یک آبجکت JSON با خصوصیات زیر است. نمونه کامل یک قانون با همه خصوصیات:

```
{
  "Name": "ServiceBus_1028",
  "RuleName": "ServiceBus_1028",
  "Path": "/esb/run/MyProcessService",
  "Limit": 5,
  "RequestCount": 5,
  "WindowInSeconds": 30,
  "TimeWindow": 30,
  "HttpMethod": "POST",
  "LimitByUser": true,
  "Condition": "FormData:action == 'approve' && Headers:X-Client == 'Portal'",
  "Message": "تعداد درخواست‌های تایید فرآیند بیش از حد مجاز است. لطفاً {0} ثانیه بعد مجدداً اقدام نمایید.",
  "IsActive": true
}

```

خصوصیت
نوع
پیش‌فرض
شرح

string
اجباری
مسیر URL اندپوینت. هنگام بارگذاری، Query String حذف و اسلش‌های ابتدا و انتها استانداردسازی می‌شود. مثال: `/Process/RunProcess`

`Limit`
int
اجباری
سقف تعداد درخواست مجاز در طول پنجره زمانی؛ باید بزرگ‌تر از صفر باشد

`RequestCount`
int
اختیاری

`WindowInSeconds`
int
اجباری

`TimeWindow`
int

`HttpMethod`

## 5. شروط پویا (Condition)

با `Condition` می‌توان قانون را فقط برای درخواست‌هایی اعمال کرد که محتوای آن‌ها شرط مورد نظر را برآورده کند. موتور ارزیابی از ساختارهای تودرتو و آرایه‌ها پشتیبانی می‌کند. پیشوندهای تعیین‌کننده منبع داده:

منبع
پیشوندها
مثال

بدنه JSON
`Body:`، `Json:`، `Payload:` یا مستقیماً نام فیلد
`Content.EndVariables[0].Value == true`

داده‌های فرم
`FormData:`، `Form:`، `FormUrlEncoded:`
`FormData:action == "submit"`

پارامترهای آدرس (Query String)
`Query:`، `QueryString:`، `QueryParams:`
`Query:isHeavy == "true"`

هدرهای درخواست
`Headers:`، `Header:`
`Headers:X-Client-Tier == "VIP"`

عملگرهای پشتیبانی‌شده:

- **مقایسه‌ای:** `==`، `!=`، `>`، `<`، `>=`، `<=`

- **متنی و مجموعه‌ای:** `contains` (شامل بودن زیررشته یا عضویت در آرایه)

- **منطقی:** `&&` (و منطقی) و `||` (یا منطقی)

## 6. اولویت‌بندی و قانون بازگشتی (Fallback)

وقتی چند قانون برای یک مسیر تعریف شده باشد، موتور آن‌ها را به این ترتیب ارزیابی می‌کند:

- ابتدا قوانین دارای شرط (`Condition`) بررسی می‌شوند. در بین آن‌ها، قانونی که Method اختصاصی دارد (مثلاً `POST`) بر قانون با Method عمومی مقدم است.

- در صورت برقراری شرط یک قانون، همان قانون انتخاب می‌شود و بررسی پایان می‌یابد.

- اگر هیچ‌یک از شروط برقرار نباشد، قانون عمومی بدون شرط به‌عنوان سهمیه پایه (Fallback) اعمال می‌شود.

برای مثال، می‌توان برای یک مسیر یک قانون شرطی با سقف کم و یک قانون بدون شرط با سقف بالاتر تعریف کرد تا درخواست‌هایی که شرط را ندارند با سقف پایه محدود شوند.

## 7. قوانین Provider و ESB در تنظیمات سیستم

تنظیماتی که در فرم وب‌سرویس منبع داده (Provider سرویس‌باس) و وب‌سرویس فرآیند (Process ESB) وارد می‌شوند، در جدول یا ستون جداگانه ذخیره نمی‌شوند. با ذخیره سرویس، قانون آن به‌صورت یک آبجکت JSON در همین تنظیم `RateLimitEndpoints` ثبت می‌شود. قواعد ثبت:

- **نام قانون (`Name` و `RuleName`):** با الگوی `ServiceBus_{Id}` ثبت می‌شود که `{Id}` کلید اصلی رکورد سرویس در جدول `ServiceBus` است؛ مثلاً `ServiceBus_1028`. به این ترتیب قانون هر سرویس از قوانین دیگر جدا می‌ماند.

- **مسیر (`Path`):** برای Provider به‌صورت `/servicebus/run/{ServiceBusName}` و برای Process ESB به‌صورت `/esb/run/{ServiceBusName}` ثبت می‌شود. با تغییر نام Service Bus، مسیر ذخیره‌شده خودکار به‌روزرسانی می‌شود.

- **سایر فیلدها:** `Limit`، `WindowInSeconds`، `LimitByUser`، `Message` و `IsActive` مستقیماً از فرم سرویس دریافت و ذخیره می‌شوند.

- **حذف سرویس:** با حذف Service Bus، قانون متناظر آن از تنظیمات سیستم و از کش حافظه فوراً پاک می‌شود.

فرم Provider و ESB فقط سقف، بازه، مبنای IP/کاربر، پیام و وضعیت فعال‌بودن را دارند. اگر لازم است قانون یک سرویس شرط (`Condition`) یا Method اختصاصی داشته باشد، باید از همین صفحه تنظیمات سیستم یا Web.Config استفاده شود.

## 8. پاسخ هنگام عبور از سقف مجاز (429)

وقتی کلاینت از سقف سهمیه عبور کند، سرور بلافاصله و بدون ورود به BPMS با کد `429 Too Many Requests` و هدرهای استاندارد پاسخ می‌دهد:

```
HTTP/1.1 429 Too Many Requests
Content-Type: application/json; charset=utf-8
Retry-After: 48
X-RateLimit-Limit: 10
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1729345200

{
    "HasError": true,
    "Message": "تعداد درخواست‌های شما بیش از حد مجاز است. لطفاً 48 ثانیه دیگر مجدداً تلاش نمایید.",
    "RetryAfter": 48
}

```

کلاینت باید مقدار هدر `Retry-After` (بر حسب ثانیه) را رعایت کند و پس از آن دوباره تلاش کند. پیام خطا همان `Message` قانون است. کد 429 به تعداد درخواست مربوط است، نه به هویت یا مجوز؛ آن را با 401 و 403 اشتباه نگیرید.

اگر محدودیت بر مبنای IP باشد و چند کاربر پشت یک IP خروجی مشترک (NAT یا Proxy) باشند، سهمیه بین همه آن‌ها مشترک می‌شود و ممکن است 429 برای همه صادر شود. در این حالت `LimitByUser` را روی `true` بگذارید یا هدر `X-Forwarded-For` را در پروکسی فعال کنید.

## 9. روش‌های دیگر تنظیم Rate Limit

Rate Limit فقط از تنظیمات سیستم قابل تنظیم نیست و در چهار محل پیکربندی می‌شود:

روش
توضیح

تنظیمات سیستم (`SystemConfiguration`)
روش همین آموزش؛ تغییرات بدون ریست سرور و زنده اعمال می‌شود

Web.Config
کلید `RateLimitEndpoints` در `appSettings` با قوانین به‌صورت رشته (جداشده با سمی‌کالن) یا JSON. تغییر آن موجب ریست دامنه کاربردی (AppDomain) و خروج موقت کاربران آنلاین می‌شود

وب‌سرویس منبع داده (Provider سرویس‌باس)
بخش «محدودیت نرخ درخواست» در فرم Service Bus؛ قانون در همین تنظیم ذخیره می‌شود

وب‌سرویس فرآیند (Process ESB)
پنجره تنظیمات وب‌سرویس فرآیند در طراح فرآیند BPMN؛ قانون در همین تنظیم ذخیره می‌شود

جزئیات هر روش در آموزش مربوط به همان روش آمده است.
